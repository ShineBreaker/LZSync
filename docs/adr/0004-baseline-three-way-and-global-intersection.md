# 基线三方判定 + 全局交集导出，而非「最近收集覆盖」

用户拍板（2026-10-26）：hub 是收全的仓库，收集只增不改、各端差异分别存；导出只导全部目标端都能接受的数据（全局交集），各端取值不同时只传播「上一轮同步以来只有一方改动」的变化，多方各改或无基线的分歧一律保留差异、交给用户。动机是让所有 fork 尽量一致，同时绝不替用户在两份都合理的数据间选边。行为细则见 `docs/design.md` §0。

## Considered Options

- 最近收集覆盖（原 HB3：canonical = 最近一次收集的整行，冲突默认 hub 覆盖目标）：实现简单，但哪端先收集决定谁赢，会静默抹掉另一端的修改。
- 纯补缺（只给缺的端新建，已存在的永不改）：最安全，但首轮之后设置、收藏、谱面新版本就再也不会传播。
- 逐端最大兼容集（每端拿它自己能接受的全部数据）：各端拿到的内容更多，但端与端之间会因支持面不同而长期不一致；用户选择一致性优先。

## Consequences

- hub 需要持久的同步基线（每端 × 同步身份的上一轮取值），一轮同步结束必须重读目标端并推进基线；冲突身份基线不推进，持续标记直到用户处置。
- 「同步身份」与「内容键」分离：谱面集按谱面身份键、键位按 (RulesetName, Variant, ActionInt)，取值（版本哈希、键组合集合）才是判定对象；版本链退为历史记录。
- 一端支持、其他端不支持的数据照收进 hub，但永不导出；新增一个支持面更窄的目标端会收窄全体的导出域。
- 新加入的端（无基线）与既有各端的分歧全部计为冲突，需用户批量处置一次。
